## User goal

Open the app at the end of the day and see today captured, without having written anything.

## User flow

1. App opens to Today view. If a draft exists, it's shown; if not, a quiet "nothing yet" state.
2. User reads the draft. Taps any sentence to edit inline (REQ-002).
3. First time a signal is relevant (first photo taken, first calendar event today), a specific
   consent prompt appears for that signal only (REQ-003) — never a bundled "allow everything" ask.

## Screens / scenes

- **Today** — the draft entry, editable inline.
- **Signal consent prompt** — one signal at a time, contextual, appears inline above the draft
  rather than as a modal interrupt.
- **Settings → Signals** — revoke any previously granted signal independently.

## Interaction model

Tap-to-edit inline, no separate "edit mode" toggle — reduces steps for REQ-002's correction flow.
Consent prompts are dismissible without penalty; declining just means that signal stays excluded.

## Visual hierarchy

Draft text is the primary visual element — quiet typography, generous whitespace, no chrome that
reads as "app UI" over "journal page." Signal consent prompts are visually secondary (smaller,
inline) so they don't dominate over the journal content itself — reinforces "ambient, not
chatbot."

## Components

Draft text block (editable), inline consent prompt, signal indicator (subtle icon showing which
signals contributed to today's draft, tappable to see which specifically).

## States

### Empty state

No signals authorized yet, or authorized but zero data today: "Nothing captured yet today." with
a single unobtrusive prompt to enable a signal — not a hard empty box.

### Loading state

Draft is generating (end-of-day trigger fired, processing in progress): a quiet pulsing text
placeholder in the draft's typography, not a spinner — matches the ambient tone.

### Error state

Generation failed (e.g. calendar fetch error): "Couldn't finish today's entry — [retry]" inline
where the draft would be, specific about what failed, not a generic error banner.

## Accessibility

VoiceOver reads the draft as body text, edit affordance announced as "Edit, double tap to edit
this entry." Consent prompts read their specific purpose text, not just "Allow Photos Access."
Dynamic Type respected in draft typography. Keyboard navigation (macOS) reaches edit, consent
accept/decline, and settings without a mouse.

## Responsive / platform behaviour

iOS: single-column, tap targets ≥44pt. macOS: same layout, adds keyboard shortcuts for edit
(Cmd+E) and settings.

## Copy rules

No "Assistant says..." framing anywhere. First person from the user's own journal, not the
system's voice. Consent prompts state the specific signal and specific use, never "to improve
your experience."

## Design assumptions

Users check the app once daily, not continuously — informs the "quiet" visual weighting over
active/urgent-feeling UI.

## Verification criteria

- Empty/loading/error states each individually screenshotable and distinguishable from one
  another and from the populated state.
- VoiceOver walkthrough covers draft, edit, and consent prompt without a sighted-only affordance.
- AC-001-03 (not chat-transcript-like), AC-002-01/02 (edit persists), AC-003-03 (specific consent
  copy) all visibly represented in this design, not just described.
