## Problem

Users want a daily journal but don't want to write one from scratch every day. They have signals
(photos taken, places visited, calendar events) that already describe what happened.

## Desired outcome

At the end of each day, the system generates a draft journal entry summarizing that day, built
from whichever signals the user has authorized (see REQ-003 for consent). The draft reads like a
quiet, ambient note — not a chatbot transcript or a bulleted log.

## Scope

- One draft entry per calendar day, generated automatically once enough of the day has passed.
- Signals in scope for v1: photos (on-device metadata only), calendar events, coarse location
  (place names, not raw coordinates).

## Non-goals

- Real-time/live journaling as the day happens — this is end-of-day, not streaming.
- Multi-day summaries or retrospectives.
- Signals beyond photos/calendar/location (e.g. health data, browser history) — future requirement
  if ever.

## Assumptions

- The user has granted at least one signal's permission; a day with zero authorized signals
  produces no draft (not an empty placeholder entry).

## Unknowns

- Exact tone/voice calibration for "ambient, not chatbot" — deferred to `design` skill's UX
  critique loop, not resolved here.

## Acceptance criteria

- AC-001-01: Given the user has authorized photo and calendar access and both have data for
  today, when the day ends (local midnight), then a draft journal entry exists summarizing today
  referencing at least one photo-derived detail and one calendar-derived detail.
- AC-001-02: Given the user has authorized zero signals, when the day ends, then no draft entry is
  generated for that day.
- AC-001-03: Given a draft entry exists, when the user views it, then it is visually and tonally
  distinguishable from a chat transcript (no "Assistant:"-style framing, no conversational filler).

## Dependencies

- REQ-003 (per-signal consent) must be implemented first — this requirement reads only signals
  REQ-003 has authorized.

## UX implications

See DES-001.

## Architecture implications

Signal ingestion needs a scheduled end-of-day trigger; deferred to an ADR if the mechanism turns
out consequential (background task scheduling on iOS has real constraints).

## Security implications

Draft generation must not transmit raw signal data (photos, coordinates) off-device unless the
user has separately authorized a specific processing step — default is on-device only.

## Privacy implications

See REQ-003 — this requirement consumes whatever REQ-003 has authorized and nothing more.

## Accessibility implications

Draft entry must be readable via VoiceOver with the same information conveyed visually (no
meaning encoded only in layout/iconography).

## Verification strategy

Runtime verification with a fixture day (seeded photos/calendar/location) asserting AC-001-01
through AC-001-03. See task-level verification plans once `plan` decomposes this.
