## Problem

(unchanged from v1) Users want a daily journal but don't want to write one from scratch every
day. They have signals (photos taken, places visited, calendar events) that already describe what
happened.

## Desired outcome

At the end of each day, the system generates a draft journal entry summarizing that day, built
from whichever signals the user has authorized. The draft reads like a quiet, ambient note.

## Scope

- One draft entry per calendar day, generated automatically once enough of the day has passed.
- Signals in scope for v1: **photos and calendar events only.** Location is explicitly out of
  scope for v1 (see Non-goals) — dropped after early tester feedback that even on-device location
  use felt invasive regardless of consent framing.

## Non-goals

- Real-time/live journaling as the day happens.
- Multi-day summaries or retrospectives.
- **Location as a signal** (moved from Scope in v1 to an explicit non-goal here) — may be
  revisited as a separate future requirement if real user demand emerges; not assumed.
- Signals beyond photos/calendar (e.g. health data, browser history).

## Assumptions

- The user has granted at least one signal's permission; a day with zero authorized signals
  produces no draft.

## Unknowns

- Exact tone/voice calibration — deferred to `design`.

## Acceptance criteria

- AC-001-01: Given the user has authorized photo and calendar access and both have data for
  today, when the day ends, then a draft journal entry exists referencing at least one
  photo-derived detail and one calendar-derived detail. *(unchanged from v1, location example
  removed from the illustrative wording)*
- AC-001-02: Given the user has authorized zero signals, when the day ends, then no draft entry
  is generated for that day. *(unchanged)*
- AC-001-03: Given a draft entry exists, when the user views it, then it is visually and tonally
  distinguishable from a chat transcript. *(unchanged)*
- AC-001-04 *(new)*: Given the app has previously stored any location-derived data from a prior
  build, when this version runs, then that data is not read or referenced by generation — the
  drop is enforced, not just unused going forward.

## Dependencies

- REQ-003 (per-signal consent) — location consent option should be removed from the consent flow
  entirely, not just left unused (see Impact below).

## UX implications

**Impact on DES-001:** the consent-prompt flow and signal-indicator component both referenced
location. `/sprout:graph`-style impact analysis on this change: DES-001 → `NEEDS_REVIEW` (not
`INVALIDATED` — the overall flow structure holds, only the location-specific consent prompt and
indicator icon need removal). A new DES-001-v2 is required before this requirement's tasks can be
planned; not included in this fixture, left as the natural next step.

## Architecture implications

Any location-permission request code and stored location data (if a prior implementation existed)
needs removal, not just disuse — see AC-001-04.

## Privacy implications

Reduces privacy surface — one fewer sensitive signal collected at all. Aligns with "privacy
first" (INT-0001) more directly than v1 did.

## Verification strategy

Runtime verification with a fixture day (seeded photos/calendar only, no location fixture) — plus
a regression check confirming no location-permission prompt appears anywhere in the consent flow
(AC-001-04).
