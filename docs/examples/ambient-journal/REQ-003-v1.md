## Problem

"Privacy is very important" (INT-0001) is not itself a testable requirement — it has to become a
concrete consent mechanism before REQ-001 can rely on any signal.

## Desired outcome

Each signal type (photos, calendar, location) has its own explicit opt-in, requested only when
first relevant, revocable independently at any time. No signal is read before its specific consent
is granted.

## Scope

Photos, calendar, location for v1 (matches REQ-001's signal scope).

## Non-goals

A general "privacy settings" redesign beyond these three signals.

## Unknowns

## Acceptance criteria

- AC-003-01: Given no consent has been granted, when the app runs, then zero signal data is
  read.
- AC-003-02: Given the user revokes a previously granted signal's consent, when the next draft
  generates, then that signal is excluded and no cached data from before revocation is used.
- AC-003-03: Given the user is asked for a signal's consent, when the prompt appears, then it
  explains specifically what that signal is used for (not a generic "allow access" dialog).

## UX implications

## Architecture implications

## Security implications

Revocation must take effect immediately, not on next app restart.

## Privacy implications

This requirement exists specifically to make "privacy first" (INT-0001) testable rather than
aspirational.

## Accessibility implications

Consent prompts must be readable via VoiceOver with the same explanation text.

## Verification strategy

Runtime verification: grant/revoke each signal independently, assert REQ-001's generation
respects current consent state at generation time, not consent state at app install.
